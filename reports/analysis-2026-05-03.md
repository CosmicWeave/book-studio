## 1. CRITICAL BUGS

### 1.1 Service Worker Path Corruption (Breaks PWA / Offline)
`scripts/sync-paths.js` prepends `/book-studio` to paths in `public/sw.js` **every build**. Since the file is read from disk each time, each run re-prefixes already-prefixed paths. After 6 runs the cache paths look like:
```
/book-studio/book-studio/book-studio/book-studio/book-studio/book-studio/
```
The SW pre-caches URLs that will **never exist**, so offline mode silently fails after repeated deploys. The same regex that fixes `'/<path>'` matches the already-doubled paths on the next run.

**Fix**: The script needs to strip any existing prefixes before applying them, or read from a canonical template file that is never modified.

### 1.2 Mixed Static/Dynamic Import of `apiClient`
The build warning `apiClient.ts is dynamically imported by historyService.ts but also statically imported by App.tsx…` means the dynamic import never produces a separate chunk — Vite keeps it in the main bundle, defeating the intent. The `historyService.ts` dynamic import should be converted to a static import.

## 2. SECURITY

### 2.1 XSS via Unsanitized HTML (OWASP A03)
Multiple locations render AI-generated or user-imported HTML with `dangerouslySetInnerHTML` **without sanitization**:
- `pages/Reader.tsx:711` — renders entire `chapter.htmlContent` directly
- `components/editor/DiffModal.tsx:46` — renders `newContent`
- `pages/DocumentsDashboard.tsx:91` — renders `doc.content`
- `components/editor/ChatModal.tsx:300` — renders AI chat responses

`marked.parse()` output is also injected unsanitized in `BookCreationModal.tsx`, `NewBookFromChatModal.tsx`, `ChatModal.tsx`, and `SequelPrequelModal.tsx`. Marked does not sanitize HTML by default. A malicious book import or AI response could inject `<script>` tags or event handlers.

**Fix**: Install [DOMPurify](https://github.com/cure53/DOMPurify) and wrap all `dangerouslySetInnerHTML` sources: `DOMPurify.sanitize(html)`.

### 2.2 No Authentication or Rate-Limiting on Backend API (OWASP A01, A04)
The Hono server has `secureHeaders()` and CORS but **zero authentication**. Any process that can reach port 3001 can:
- Read/write/delete all books, documents, and settings
- Submit arbitrary payloads to `/api/ai/generate` consuming AI quota
- Read the stored Gemini API key via `/api/ai/config`

**Fix**: For a personal/single-user deployment, add a shared-secret middleware (e.g. HTTP Bearer token from env var). Even a simple `Authorization: Bearer <TOKEN>` check prevents casual exposure.

### 2.3 Sensitive Credentials in `localStorage`
`services/googleDriveConfig.ts` stores the Google Client ID and API key in `localStorage`. These are readable by any JS on the page (XSS amplification), browser extensions, and dev tools sharing.

**Fix**: Store credentials in `sessionStorage` at minimum, or keep them in memory only (re-entered each session) if they don't need to persist across restarts.

## 3. PERFORMANCE

### 3.1 Single 1.76 MB JavaScript Bundle
The entire app ships as one chunk (`index-d4ZisN4m.js`, 1.76 MB / 500 KB gzipped). There is **no code splitting and no `React.lazy()`** anywhere. Heavy libraries (PDF.js, TipTap, pdfjs-dist) load even on the dashboard where they're never used.

**Suggested manual chunks for `vite.config.ts`**:
```ts
manualChunks: {
  'vendor-react': ['react', 'react-dom', 'react-router-dom'],
  'vendor-tiptap': ['@tiptap/core', '@tiptap/react', '@tiptap/starter-kit'],
  'vendor-pdf': ['pdfjs-dist'],
  'vendor-epub': ['turndown', 'turndown-plugin-gfm'],
}
```
And lazy-load the `BookEditor` and `Reader` routes since they pull in TipTap.

### 3.2 No `React.memo` on Any Component
121 `useCallback`/`useMemo` usages exist, but **zero `React.memo()` wraps**. High-frequency re-render sources like `BookCard` (rendered in a list), `Toast`, and all sidebar items re-render on every `AppContext` state change (which is very frequent due to `fetchData` calls after every write).

**Fix**: Wrap list-item components (`BookCard`, `ReadingBookCard`) and the `Sidebar` with `React.memo`. Split `AppContext` into a stable `DataContext` and a more volatile `UIContext` (already noted in `todo.md` §10).

### 3.3 `fetchData()` Called After Every Mutation
`createNewBook`, `deleteBook`, `restoreBook`, `archiveBook`, `updateBook`, and others all call `fetchData()` — which re-fetches **all books, series, macros, documents, and settings** from the server. For a large library, this is 5 HTTP requests on every user action.

**Fix**: Apply optimistic updates (update local React state immediately) and only use `fetchData()` for reconciliation after conflicts or on initial mount.

## 4. TYPE SAFETY

### 4.1 TypeScript `strict` Mode Disabled
`tsconfig.json` has no `strict`, `noImplicitAny`, or `strictNullChecks`. The codebase has **306 usages of `any`** (including `e: any` in 144 catch blocks) and many non-null assertions (`!`). This hides entire categories of runtime errors from the compiler.

**Fix**: Enable `"strict": true` incrementally — start with `"strictNullChecks": true` and address the resulting errors, then `"noImplicitAny"`.

### 4.2 Untyped Error Handling
Pattern `catch (e: any) { toastService.error(e.message) }` is used 144 times. If `e` is a string or non-Error object, `.message` is `undefined` and the toast shows nothing.

**Fix**: Use a helper: `function getErrorMessage(e: unknown) { return e instanceof Error ? e.message : String(e); }`

## 5. ARCHITECTURE

### 5.1 Duplicate `BookEditor` Component
There are two files serving overlapping purposes:
- `components/BookEditor.tsx` (535 lines)
- `pages/BookEditor.tsx` (551 lines)

Both read `bookEditorViewSettings` from `localStorage`, handle the same sidebar panels, and render `ChapterEditor`. This is a maintenance hazard — changes must be made in both places.

### 5.2 Monolithic `BookEditorContext` (1030 lines)
The context mixes AI generation logic, chapter management, image editing, outline handling, audiobook state, and save/autosave. This makes testing difficult (a single context test file needs 874 lines), re-renders expensive, and cognitive load high.

**Suggested split**:
- `ChapterContentContext` — content state and edit handlers
- `GenerationContext` — all `gemini.*` calls and loading flags
- `BookMetaContext` — title, outline, series, save status

### 5.3 Dead Code: `services/db.ts`
`services/db.ts` (442 lines, full IndexedDB implementation) still exists alongside `services/apiClient.ts`. It is no longer imported by anything active but remains in the bundle. The coverage report shows 0% coverage on it.

**Fix**: Delete `services/db.ts` or move it to an `_archive/` folder; it's dead weight and confuses contributors.

### 5.4 `App.tsx` God Component (582 lines)
`MainApp` manages sidebar state, scroll restoration, swipe gestures, offline detection, drag-and-drop file restore, backup checking, conflict resolution, command palette, and all routing. It should be broken into custom hooks (`useScrollRestoration`, `useSwipeGesture`, `useDropRestore`, etc.) to keep the component readable.

## 7. BUILD & DEPLOYMENT

### 7.1 CDN Dependencies Without Integrity Hashes
`public/sw.js` pre-caches CDN URLs like `https://cdn.tailwindcss.com` and `https://esm.sh/...` with no Subresource Integrity (SRI) check. A compromised CDN could serve malicious scripts that the SW would cache and serve indefinitely.

### 7.2 Vendor Scripts Without `type="module"`
`index.html` loads `vendor/jspdf.umd.min.js` and `vendor/html2canvas.min.js` as plain `<script>` tags, triggering a Vite build warning. These become globals, can't be tree-shaken, and block the parser.

### 7.3 `index.css` Missing at Build Time
The build logs `index.css doesn't exist at build time, it will remain unchanged to be resolved at runtime`. If Tailwind CDN fails to load, the app has no fallback styles. The CSS should be part of the build pipeline (PostCSS/Tailwind CLI) rather than a CDN.

## 9. CODE QUALITY

- **101 `console.log/warn/error` statements** remain in production code (excluding tests). These pollute the browser console and leak implementation details.
- **Tailwind via CDN** in production — this loads the full ~3 MB Tailwind CSS file rather than a purged subset. This should be replaced with a PostCSS build step.
- **`(e as any).message`** pattern is widespread — would be eliminated by `strict` mode.
